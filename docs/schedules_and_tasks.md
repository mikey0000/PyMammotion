# Schedules / Tasks (Job Plans) — Fetch, Sync, and Storage

Reverse-engineered from Mammotion 2.3.8.201 APK, cross-checked against 2.2.4.13, and matched against the pymammotion implementation.

## TL;DR

Schedules are fetched on demand, triggered by a **hash-based staleness signal** (`initCfgHash`) that the device includes in work-report messages — not by periodic polling.  Our implementation uses a simpler **count-based** staleness flag (`plans_stale`) rather than a hash comparison.  There is no equivalent of the map's `bol_hash` round-trip check on the pymammotion side.

---

## 1. APK — what triggers a fetch

The device embeds three hashes in every `WorkEvent` / work-report message:

| Hash field | Covers |
|---|---|
| `initCfgHash` | Main config including job plans |
| `ubEcodeHash` | Error code configuration |
| `ubZoneHash` | Zone/area config (also updated mid-mow) |

`DeviceInitializationManager.updateInitHash()` compares each incoming hash against the locally cached value.  On mismatch it sends:

```
allpowerfullRW(id=5, context=1, rw=1)   → fetch plans
allpowerfullRW(id=5, context=2, rw=1)   → fetch error config
allpowerfullRW(id=5, context=3, rw=1)   → fetch zone config
```

Up to 10 retries with exponential back-off.  There is **no periodic timer** — only hash-change events start a fetch.

`ubZoneHash` is also watched while the device is actively mowing and triggers an immediate re-fetch if it changes mid-session.

## 2. APK — protobuf messages

| Direction | Message | Proto field | Carries |
|---|---|---|---|
| device → app | `NavPlanJobSet` | `todev_planjob_set` (SubNavMsg case 15) | One complete plan |
| device → app | `SysJobPlanTime` | `plan_job_set` (SubSysMsg) | Time-based plan + nested `SysJobPlan` |
| device → app | `SysPlanJobStatus` | `TOAPP_PLAN_STATUS` (SubSysMsg case 18) | Plan execution status flag |
| app → device | `NavTaskCtrl` | `NAV_TODEV_TASKCTRL` (code 14) | Start / pause / stop / resume |

`NavPlanJobSet` carries the full plan definition: `planId`, `jobId`, `taskId`, `jobName`, `taskName`, `startTime`, `endTime`, `startDate`, `endDate`, `area`, `workTime`, `routeModel`, `routeSpacing`, `routeAngle`, `speed`, `knifeHeight`, `week`, `weeks[]`, `intervalDays`, `rainSolution`, `towardMode`, `ultrasonicBarrier`, `zoneHashs[]`, `jobplanSwitch`, `mowingLaps`, `pathOrder`, `requiredTime`, `remainedSeconds`, `result`, `triggerType`, `version`, `reserved`.

---

## 3. APK — local storage

Plans are persisted to a SQLite table (`JobPlanDB`) via LitePal ORM.  The key fields that differ from the wire message are:

- `deviceId` / `userId` — scoped per account+device
- `version` — plan version number for optimistic concurrency
- `serverId` — server-side reference if synced to cloud
- `gmtCreate` — client-side creation timestamp

Re-fetching replaces existing rows by `planId`.  The `BleJobPlanListener` interface notifies UI subscribers after each update.

## 4. pymammotion — data model

### Mower (Luba / Yuka)

```
MowerDevice.map.plan: dict[str, Plan]      # keyed by plan_id
MowerDevice.map.plans_stale: bool
```

`Plan` lives in `pymammotion/data/model/hash_list.py`.  Notable fields:

- `plan_id` — 21-char string (13-digit ms timestamp + 8 random digits 0–8, generated by `new_mower_plan_id()`)
- `zone_hashs: list[int]` — area hashes this schedule will mow
- `reserved: bytes` — 8-byte buffer; byte index 2 encodes the enable/disable flag
- `total_plan_num` / `plan_index` — pagination envelope fields, not part of the plan identity
- `is_enabled()` / `with_enabled()` / `with_renamed()` — mutation helpers

`update_hash_lists()` prunes plans whose `zone_hashs` reference areas that no longer exist in `self.area` — keeping plan storage consistent with the area manifest.

### Spino (pool cleaner)

```
PoolCleanerDevice.plans: dict[int, PoolPlan]   # keyed by jobid (int)
PoolCleanerDevice.plans_stale: bool
```

Wire field `enable` is **inverted** on decode (`enable=0` means enabled on the wire).

## 5. pymammotion — staleness detection

Unlike maps (which use `bol_hash` for a precise content-hash check), plans use a simpler **count comparison**:

**Mower:** `all_plan_task` message delivers a list of plan IDs the device currently holds.  If any ID is absent from `device.map.plan`, the state reducer sets `plans_stale = True`.

**Spino:** `plan_job_set` includes `totalplannum`.  If `totalplannum > len(device.plans)`, reducer sets `plans_stale = True`; clears it when counts match.

There is no hash-based check equivalent to `is_map_synced()`.

## 6. pymammotion — fetch sagas

| Saga | File | Trigger |
|---|---|---|
| `PlanFetchSaga` | `pymammotion/messaging/plan_saga.py` | `plans_stale = True` on mower |
| `SpinoPlanFetchSaga` | `pymammotion/messaging/spino_plan_saga.py` | `plans_stale = True` on Spino |

`PlanFetchSaga` sends `read_plan(sub_cmd=2, plan_index=0)` and collects `todev_planjob_set` responses until `total_plan_num` is satisfied.  Max 3 attempts, 2 s step timeout.

`SpinoPlanFetchSaga` mirrors this using `read_spino_plan(plan_index=0)` / `ctrl.plan_job_set`.

## 8. HA coordinator sync

`async_sync_schedule()` in `coordinator.py` sends `read_plan(sub_cmd=2, plan_index=0)` directly (outside a saga).  `mower_api.py` gates this behind a 30-minute polling interval and only calls it when `total_plan_num != len(device.map.plan)`.

HA-facing CRUD lives in `pymammotion/homeassistant/mower_api.py`:
- `create_mower_task`, `edit_mower_task`, `rename_mower_task`, `set_mower_task_enabled`, `delete_mower_task`, `copy_mower_task`
- Spino equivalents: `create_spino_task`, `edit_spino_task`, `delete_spino_task`, `delete_all_spino_tasks`, `copy_spino_task`

---

## 9. Gap vs APK

The APK uses `initCfgHash` for precise hash-based invalidation (same pattern as `bol_hash` for maps).  pymammotion currently has no equivalent — it relies on the count-based `plans_stale` flag and a 30-minute polling fallback.  A hash-based watcher (similar to the `bol_hash` watcher in `client.py`) watching `initCfgHash` from work-report messages would be the correct long-term fix.
