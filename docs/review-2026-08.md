# Architecture Review — 2026-08-31

Reviewed at commit `d8081ec` with the working tree's in-flight refactor applied
(the `utility/` → `data/model` + `render/` moves, `client.py`'s split into
`client_auth` / `ble_inventory` / `inbound_router` / `auto_fetch`).

Baseline measured, not assumed:

| check | result |
|---|---|
| `ruff check pymammotion/` | clean |
| `ruff format --check pymammotion/` | 144 files already formatted |
| `ty check pymammotion/` | clean |
| `pytest tests/ -m "not live"` | 1561 passed, 8 deselected, in 31 s |
| bare `except:` | none |
| function-body imports | none (the convention holds everywhere) |
| `asyncio.get_event_loop()` | 1, in vendored `aliyun/tea/core.py` |
| cross-module private access | 4 `noqa: SLF001` total |

**What is working.** The layering is real and enforced by tests, not just
described. Decomposition is proceeding by extraction with a stated rationale for
mixin-vs-collaborator each time. `LoopHost` turning ~22 implicit private reads
into a typed Protocol is the right instinct. `transfers.py` choosing free
functions over base-class helpers, on the evidence that optional base-class
utilities weren't being adopted, is a genuinely good call. The invariants in
`CLAUDE.md` are unusually well reasoned and several are pinned by tests.

The findings below are what remains.

## Structural

### S1. `DeviceHandle` is the last god object — 2280 lines, 104 attributes, ~90 methods

`client.py` has had four collaborators pulled out of it. `handle.py` has had
none: the loops moved out as free functions, but every piece of state they touch
stayed. Two blocks are cohesive enough to leave on their own terms:

- **Report-stream control**, `handle.py:1371-1700` (~330 lines): `request_report_snapshot`,
  `start_report_stream`, `_send_rpt_start_verified`, `_send_report_stream_start`,
  `send_report_stream_keep`, `_send_report_stream_stop`, `_fire_report_stream_stop`,
  `send_one_shot_report`, `request_reports`, `enqueue_ble_stream_command`,
  `_wait_for_report_data`. This is a start/keep/stop protocol state machine with
  its own verification and BLE/MQTT divergence — not handle plumbing. The port it
  needs already exists: `LoopHost`.
- **Subscription plumbing**: `_DebouncedBus` plus the eight `subscribe_*` /
  `watch_field` methods and their buses.

Extracting the first would take `handle.py` under 2000 lines and give the
report-stream logic a place where its own tests can address it directly.

### S2. `DeviceRegistry` is buried at `handle.py:2164`

Its sibling `AccountRegistry` has a package (`account/registry.py`). The
asymmetry means anything that needs a device lookup imports the 2280-line handle
module. Move it to `device/registry.py`.

### S3. `Transport` ABC violates interface segregation — BLE inherits a cloud API — ✅ FIXED

`transport/base.py` puts on the abstract base a body of machinery
`BLETransport` never uses (verified: zero references in `transport/ble.py`):

- the 12-hour send quota — `_SEND_LIMIT`, `_RATE_LIMIT_DURATION`, `_SEND_WINDOW`,
  `record_send`, `sends_in_window`, `is_rate_limited`, `set_rate_limited`,
  `version_is_rate_limited`, `is_send_blocked`, `seconds_until_send_available`
- the auth-failure flags — `on_auth_failure`, `mark_auth_failed`,
  `mark_unrecoverable_auth_failure`, `is_unrecoverable_auth_failure`
- four cloud message callbacks — `on_device_status`, `on_device_event`,
  `on_device_properties`, `on_device_mammotion_properties`

The leak is visible in the signature the base forces on BLE:

```python
async def send(self, payload: bytes, iot_id: str = "", firmware_version: str = "1.0.0.0") -> None:  # noqa: ARG002 — Transport.send signature
```

`BLETransport` also has to override `is_usable` because the base computes it from
cloud auth flags. This is the one place the codebase's own rule — "new default
behaviour goes on the base class" — produced a base a subclass must ignore.

**Fixed:** `transport/cloud.py` holds `CloudTransport`; both MQTT transports
inherit it and `BLETransport` stays on the thin base, which is down from 597 to
404 lines and now carries nothing BLE doesn't use. `ty` surfaced three call sites
that had been silently untyped, including a `transport_type != BLE` string-tag
test standing in for the missing type. `on_fatal_auth_error` — the one cloud
callback never hoisted, and consequently declared twice with divergent parameter
types — is now unified. Rationale and full detail in `docs/decisions.md` D13.

### S4. `client.py` is 2189 lines and ~80 methods after three extractions

The remaining mix is device/transport lifecycle, nine saga entry points, RTK and
camera-stream HTTP pass-through, geojson regeneration, and command send. The
cheapest win first: seven of the saga entry points open with a verbatim

```python
handle = self._device_registry.get_by_name(device_name)
if handle is None:
    _logger.warning("<caller>: device '%s' not registered", device_name)
    return
```

Extract `_require_handle(name, caller)`. `start_plan_sync` /
`start_spino_plan_sync` are otherwise near-identical and could share one body.

## Correctness and robustness

### C1. `send_raw` reports success for a rate-limited send that never went out — ✅ FIXED

`handle.py:1917` catches `TransportRateLimitedError`, logs a warning, and
returns normally. Every other branch in that `except` chain either re-raises or
falls back to a second transport. So `send_command_with_args` — the HA-facing
path — completes without error for a command the device never received. The
caller has no way to learn this.

**Fixed:** the `except TransportRateLimitedError` clause is gone, so the error
propagates to the queue, whose demotion buckets already classify it at WARNING.
`_send_marked`'s own pre-flight now names the remaining block time in the
exception, since the queue logs the exception text and the discarded local
warning was the only place that figure appeared. Two existing tests pinned the
swallow as intended behaviour and were rewritten to expect the raise while
keeping their real assertion (a guard trip must not call `set_rate_limited()`
again). Regression coverage: `tests/unit/device/test_send_raw_rate_limit.py`.

### C2. The main command API is stringly typed

```python
async def send_command_with_args(self, name: str, key: str, ..., **kwargs: Any) -> None:
    ...
    command_bytes: bytes = getattr(commands, key)(**kwargs)
```

This is the primary entry point HA uses for every device command, and it is
invisible to `ty`, to editors, and to rename refactors. Renaming a builder in
`mammotion/commands/messages/` breaks the integration silently — surfacing as
`AttributeError` at runtime, inside a queue task. A wrong kwarg surfaces as
`TypeError` in the same place. At minimum, constrain `key` to a
`Literal[...]` generated from `MammotionCommand`'s public methods, so a rename
becomes a type error on both sides.

### C3. `DeviceRegistry.get` / `.unregister` change meaning by arity

`get(account_id, device_id)` addresses an exact key; `get(device_id)` resolves
across accounts — through a parameter still named `account_id`. `TODO.md` H5
records a real bug produced by exactly this ambiguity (`connect_ble` passing a
device name into the account slot). Split into `get(account_id, device_id)` and
an explicitly named `get_any_account(device_id)`.

### C4. Nested walrus in `DeviceConfig.get_device_config`

```python
if found := self.inner_list.get(int_mod_or_key) or (found := self.default_list.get(int_mod_or_key)):
    return found
```

The inner assignment is dead — the outer one overwrites it with the same value.
Correct by accident, and it reads as if it does something. It also treats an
empty-dict config as "not found". Write it as two lines.

## Public surface and packaging

### P1. The package version is wrong and unmaintained — ✅ FIXED

`pymammotion/__init__.py` declares `__version__ = "0.0.5"`; `pyproject.toml`
says `0.8.14`. The cause is in `[tool.bumpver.file_patterns]`, which targets
`src/pymammotion/__init__.py` and `setup.cfg` — **neither file exists** (this is
not a `src/` layout and there is no `setup.cfg`). So `./bin/bumpver update` has
been updating only `pyproject.toml` and `README.md`, silently, since the layout
changed. Fix the target path, or drop the constant and derive it:

**Fixed:** `__version__` is now `0.8.14`, and the bumpver patterns point at
files that exist. The README was drifted too — it carried `0.8.5` in the badge
label and `0.7.31` in the badge URL, because bumpver searches for the *old*
version string and neither matched. All four targets are now synced and verified
with `bumpver update --patch --dry`, which correctly rewrites `README.md` (both
strings), `pymammotion/__init__.py`, `[project] version` and `current_version`.

Left alone, but worth a look: `[tool.setuptools.package-data]` in
`pyproject.toml` is inert — the build backend is hatchling. There is also a
`py.typed` at the repo root, outside the package, alongside the real
`pymammotion/py.typed`.

### P2. The package's headline export is the legacy BLE stack

```python
__all__ = ["MammotionBLE", "MammotionHTTP", "logger"]
```

`MammotionBLE` (`bluetooth/ble.py`, 76 lines) is a standalone bleak wrapper with
no library consumers — only two `examples/` scripts — and it is entirely
disjoint from `transport/ble.py::BLETransport`, which is the actual BLE stack.
Meanwhile `MammotionClient`, which the module docstring names as *the* entry
point, is not exported at all. A newcomer following `__all__` lands on the wrong
BLE implementation.

### P3. Two event systems

`pymammotion/event/` defines `Event`, `MoveEvent` and `DataEvent`, none of which
has a consumer; only `BleNotificationEvent` is used, by `bluetooth/ble.py` —
i.e. by P2's legacy stack. The live mechanism is `transport/base.py`'s `EventBus`
+ `Subscription`, used throughout. The `event/` package should go with P2.

### P4. ~700 lines of dead code, in a repo whose `dead_code.md` says it was cleaned

Verified zero consumers anywhere in `pymammotion/` (and, where noted, in
`tests/` too):

| module | lines | note |
|---|---|---|
| `mammotion/control.py` | 160 | joystick; `dead_code.md` claims `mammotion/control/` was deleted |
| `utility/rocker_util.py` | 180 | only consumer is `utility/movement.py` |
| `utility/movement.py` | — | only consumer is `mammotion/control.py` |
| `data/model/raw_data.py` | 231 | no consumers, no tests |
| `data/model/account.py` | — | no consumers, no tests |
| `event/event.py` (3 of 4 classes) | — | see P3 |

The joystick chain is why `pyjoystick` and `nest-asyncio` sit in the `extras`
dependency group. Its one remaining reference, `examples/test_control.py`,
imports `pymammotion.mammotion.control.joystick` — a package path that no longer
exists, so the example is already broken.

`data/model/mowing_modes.py` also has no in-library consumer, but
`DetectionStrategy.for_device` is tested and is a documented firmware gate the HA
integration calls directly. Keep it — and say so in the module docstring, or the
next dead-code sweep deletes it.

### P5. `data/model/device_capabilities.py` is 2629 lines, ~2350 of them literal data

A per-product-key capability table (blade height, speed, path spacing, area
limits) hardcoded as Python dict literals. It belongs in
`pymammotion/resources/` as JSON — the package already ships `resources/ca.pem`,
and `scripts/device_configuration_form.json` suggests the data arrived as JSON
in the first place. As code it can't be schema-validated, diffed usefully, or
updated by anyone who doesn't edit Python.

### P6. Three modules named for the same idea

`data/model/device_config.py` (`OperationSettings`),
`data/model/device_capabilities.py` (`DeviceConfig` limits), and
`utility/device_config.py` (a shim re-exporting the second). `mower_api.py`
imports two of them on adjacent lines:

```python
from pymammotion.data.model.device_capabilities import DeviceConfig
from pymammotion.data.model.device_config import OperationSettings, create_path_order
```

Rename `data/model/device_config.py` to what it holds — `operation_settings.py`.

## Tooling and hygiene

### T1. CI lints only changed files

`.github/workflows/on-push.yml` computes a changed-file list and runs
`ruff check ${{ files }}`. A newly enabled rule, or a file moved by a rename, is
never swept. `ruff check pymammotion/` passes repo-wide today, so switching to
the full path costs nothing and closes the hole.

### T2. CI never runs `ty`

Type checking is a pre-commit-only gate. Anyone committing with `--no-verify`,
and any PR that doesn't run local hooks, skips it entirely. It passes today; add
`uv run ty check pymammotion/` to the build job.

### T3. `tests/fakeserver` is a live-socket fake with no timeout guard

Not a current failure — the suite is fast and green (1561 in 31 s, and the
`fake_cloud` integration tests are 15 s of that). The risk is that
`tests/fakeserver` binds real HTTP and MQTT sockets, so a future test that
awaits a message the fake never sends hangs the run rather than failing it, and
pre-commit runs the whole suite on every commit. A `pytest-timeout` default
(`timeout = 60` in `[tool.pytest.ini_options]`) turns that class of mistake into
a failure with a traceback. Cheap insurance for a suite this size.

### T4. Repo-root clutter

Untracked at the root: `output.txt` (1 MB), `t`, `bytes.py`, `areas.json`,
`final_svg_test.py`, `generate_geojson_test.py`, `test_svg_implementation.py`,
`HA_messages_L2.txt`, `MQTT_messages_L2.txt`, `MQTT_invoke_L2.txt`,
`online_notification.txt`. Three are named `*test*` and live outside `tests/`.
Move what is worth keeping into `examples/` or `tests/`; gitignore the capture
logs.

### T5. The three review documents at the root are untracked and stale — ✅ DONE

`ARCH_ISSUES.md`, `TODO.md` and `dead_code.md` are not in git, so nothing keeps
them honest. Spot-checking every "Critical" item in `TODO.md` found all four
already fixed:

| item | status |
|---|---|
| C1 bare `except:` in `_full_relogin` | fixed — no bare `except:` remains; the method is gone |
| C2 saga-task crash deadlocks the queue | fixed — `command_queue.py` releases `_exclusive_active` in an unconditional `finally` |
| C3 broker race on pending-future resolution | fixed — `set_result` now happens inside `async with self._lock` |
| C4 unsynchronised `_rate_limited` flag | fixed — replaced by `Transport.set_rate_limited()` |

`H2` (the `assert self._token_manager` that `python -O` strips) and `H7`
(`TooManyRequestsException` positional args) are fixed too. `dead_code.md`
records deletions that have since come back (P4). Stale review docs are worse
than none: they misdirect the next reader.

**Done:** the design rationale worth keeping — why no `MQTTBaseTransport`, why
saga mechanics are free functions, why there are no auth rate limiters — is now
`docs/decisions.md`. The items that are genuinely still open are in "Carried
over from the previous review" below. `ARCH_ISSUES.md`, `TODO.md`,
`dead_code.md` and `dynamics_line.md` are deleted.

### T6. Three different Python versions are declared

| declaration | value |
|---|---|
| `.python-version`, venv | 3.13 |
| `pyproject.toml` `requires-python` | `>=3.13` |
| `[tool.pylint] py-version` | `3.13` |
| `[tool.ty.environment] python-version` | **`3.12`** |
| `CLAUDE.md` "Key Conventions" | **3.12+** |

`ty` is therefore type-checking against 3.12 semantics for a package that will
only install on 3.13 — so a 3.13-only construct reads as an error, and 3.12
stdlib shapes that changed in 3.13 are checked against the wrong one. Set
`[tool.ty.environment] python-version = "3.13"` and fix the `CLAUDE.md` line.

## Carried over from the previous review

The root-level `ARCH_ISSUES.md`, `TODO.md` and `dead_code.md` have been removed:
their design rationale is now `docs/decisions.md`, and every item was re-checked
against the code. These are the ones still open. All are minor — the substantive
findings are above.

| item | where | status |
|---|---|---|
| `_logger.warning(ex)` logs a bare exception | `client.py:515` | open — use `"...: %s", ex` |
| `str(exc)` in auth error messages loses the type | `token_manager.py` ×5 | open — `f"{type(exc).__name__}: {exc}"` |
| `skip_if_saga_active` is checked outside the lock that guards saga lifecycle | `command_queue.py:153` | open — low frequency, benign either way |
| Sagas clear `self.result` inside `_run`, so a consumer can read stale state before the run starts | `map_saga.py:128` and peers | open — reset in `__init__` or a `reset()` the queue calls |
| `Saga.device_name` is a class attribute defaulting to `""`, but `map_saga` / `mow_path_saga` take a constructor argument and store `self._device_name` instead — two spellings, and four sagas accept neither | `messaging/` | open — decide whether it becomes a required constructor argument (uniform, touches every construction site including HA) or the concrete sagas standardise on `self.device_name` |
| `step_timeout` / `total_timeout` are class constants with no per-instance override | `saga.py:50-51` | open — accept them in `__init__` for slow-network devices |

Verified fixed since those documents were written, and dropped: every "Critical"
item (queue deadlock, broker future race, `_rate_limited` synchronisation, bare
`except:`), `H1`–`H8` (silent `skip_planning` failure, `python -O`-stripped
assert, BLE cross-thread disconnect, silent BLE write failure, `connect_ble`
key confusion, `SLF001` private access — now zero in `client.py` —
`TooManyRequestsException` positional args, the broad `except` in the activity
loop), `M4`–`M6`, `M9`–`M13`, `M15`–`M17`, `L1`–`L3`, `L6`, `L7`, and
`A1`, `A3`–`A8`. `A5` in particular is resolved by the split into
`mqtt_loop` / `ble_loop` / `dynamics_line_loop` behind the `LoopHost` Protocol
with the cadence tables in `modes.py` and `poll_policy.py`.

The root-level `dynamics_line.md` gap list was also re-checked and removed. Four
of its six items are done — `device/dynamics_line_loop.py` now polls on the
APK's 10 s cadence, re-checks `is_support_dynamics_line` per tick (LUBA_VA is
firmware-gated and firmware isn't known at loop start), and the `hash_num=0`
item was a non-issue by its own admission. Three remain:

- `MammotionClient.get_dynamics_line` — the manual entry point — has no
  `is_support_dynamics_line` gate, unlike the loop that replaced its polling role.
- Its docstring says the APK uses "a 1-second minimum gap"; the APK uses 3000 ms,
  and no gap is enforced on this path at all.
- Nothing clears `device.map.dynamics_line` when the device leaves
  `MODE_WORKING`. The APK drops `dynamicsLineListMap` on that transition, so a
  finished session's path persists into the next view.

A handful of purely stylistic entries (`M1` walrus consistency, `M18` closure
capture, `L4`) were dropped rather than re-litigated.
